# Миграции

### ***Обязательно после каждого изменения схемы разработчик должен сгенерировать миграцию***

Миграции используются для накатывания изменений схемы на продовые серверы, поэтому важно генерировать миграционные файлы с учётом предыдущей миграционной истории.

### Общий процесс для работы с миграциями
1. Внести изменения в схему базы данных (`schema/core.sql`).
2. Поднять локальную БД по миграциям (см. [Предварительные шаги](#предварительные-шаги)).
3. Запустить команду `./scripts/migrate.sh make-migration` для создания нового файла миграции (см. [Создание миграций](#создание-миграции)). Это создаст новый файл в директории `migrations` и обновит файл `changelog.xml`.
4. ***ОБЯЗАТЕЛЬНО*** Проверить созданный миграционный sql файл на наличие ошибок. Автосгенерированный скрипт может не включать некоторые изменения (создание функций, процедур, схем), а также не учитывает "перекладывание" данных. Все эти изменения должны быть добавлены вручную (и прописаны команды отката, начинающиеся с `--rollback`).
5. Если всё прошло успешно, миграционный скрипт и изменения в `migrations/changelog.xml` добавить в коммит.

### Предварительные шаги:
1. Создаём текущую эмуляцию схемы продовой базы (назовём её `preprod`).
```bash
docker compose -f compose.yaml -f compose.test.yaml up -d db
docker exec la2028-database-db-1 psql -U postgres -s postgres -c "CREATE DATABASE preprod;"
```
2. Мигрируем в неё текущую схему через миграции.
```bash
./scripts/migrate.sh update --db preprod --url localhost:5432
```
Теперь можем использовать воссозданную БД как основную для создания миграций.

### Создание миграции

Все манипуляции с миграциями происходят через скрипт `scripts/migrate.sh`.
При необходимости логины и пароли задаются через `--user(--ref-user) --password (--ref-password)`.

Для создания миграции из БД `postgres` (рабочая) в БД `preprod` (последняя версия БД после закоммиченных миграций):

```bash
./scripts/migrate.sh make-migration --url localhost:5432 --db preprod --ref-url localhost:5432 --ref-db postgres --script test_migration.sql
```

В папке `migrations/` будет создан файл `YYYYMMDD_HHMMSS_test_migration.sql`, а также добавлены строки об этой миграции в `migrations/changelog.xml`.

***Важно!*** сгенерированные sql файлы надо просмотреть самостоятельно: нет гарантии, что все изменения будут там отображены (команды типа `create function` добавляются вручную).

### Применение миграций

* С явным указанием sql скрипта миграции (применяется только она):
```bash
   ./scripts/migrate.sh update --url localhost:5432 --db preprod --script ./migrations/test_migration.sql
```

* с указанием changelog.xml (по умолчанию) — последовательно применяются все неприменённые миграции:
```bash
   ./scripts/migrate.sh update --url localhost:5432 --db preprod
```

### Откат миграций

Основной параметр — `--tag`, который принимает название миграционного скрипта, до состояния которого нужно откатить схему.

Например, откатим изменения до состояния, соответствующего миграции `baseline.sql`:

```bash
   ./scripts/migrate.sh rollback --url localhost:5432 --db preprod --tag 20261116_000000_baseline.sql
```

### "Пометить" базу данных как смигрированную

Когда БД уже развёрнута и хранит данные и удалять её нельзя:

```bash
   ./scripts/migrate.sh fake-update --url localhost:5432 --db preprod --tag 20261116_000000_baseline.sql
```

После этого в БД создаются таблицы миграционной истории `databasechangelog` и `databasechangeloglock`.

### На что обратить внимание в автосгенерированных скриптах

1. Всегда помнить, что изменения должны быть максимально безопасны для данных.
2. В скрипте может не хватать команд миграции (автоматизация настроена только для части типов изменений).
3. Обязательно проверить логику отката (комментарии с sql командами, начинающиеся с `--rollback`).
4. Функции/процедуры, перечисления и данные в таблицах-словарях переносятся в миграционный scrипт вручную (as-is), с учётом существующих записей.
